# Enzoic for Delinea Secret Server

Sweep a Delinea Secret Server vault and check every password against
[Enzoic](https://www.enzoic.com)'s compromised-credentials database.

It answers the question a customer asks first: **what is already bad in
there?**

**Read-only.** Neither integration ever writes to Secret Server. The only thing
either one writes is a CSV report on your own filesystem, and the report never
contains passwords.

```
    12  \Finance        sql-prod-sa    svc_sql      <14 chars>  [Clean]
    18  \Finance        legacy-ftp     ftpuser      <9 chars>   [Compromised]  2,647,331 exposures
    23  \Service Accts  backup-runner  svc_backup   <16 chars>  [Weak]
    31  \Service Accts  vendor-portal                           (requires check-out - skipped)
```

## Two implementations

The same tool, twice, because "install Python on the PAM box" is not always an
available answer.

| | [`powershell/`](powershell/) | [`python/`](python/) |
|---|---|---|
| Runtime | Windows PowerShell 5.1 or PowerShell 7+ | Python 3.11+ |
| Dependencies | **none** — no modules to install | `requests` |
| Config file | `.psd1` or `.json` | `.toml` or `.json` |
| Runs on | Windows | Windows, Linux, macOS |
| Tests | 64, fully offline | 66 on Windows, 59 elsewhere, fully offline |

**They are at parity.** Same endpoints, same verdicts, same read-only
guarantee, same config keys, same report format. Anything that is true of one
is true of the other unless a README says otherwise — and each README has a
short, explicit section listing the deviations that remain.

Config keys are matched case- and separator-insensitively, so `BaseUrl`,
`base_url` and `base-url` are one key. DPAPI-encrypted values are
wire-compatible in both directions: a blob generated by the PowerShell version
decrypts in the Python one and vice versa, and there is a test in each suite
asserting exactly that against the other implementation.

**Which to pick:** PowerShell, if the host is Windows and you want nothing
installed. Python, if the scan runs from Linux, or from a container, or you
want the objects in a pipeline that is already Python.

## Start here

1. **[docs/secret-server-setup.md](docs/secret-server-setup.md)** — the Secret
   Server account, the two permission grants people miss, the Enzoic API key,
   and the API notes. This applies to both and is worth reading once.
2. **[powershell/README.md](powershell/README.md)** or
   **[python/README.md](python/README.md)** — installing, configuring, running,
   scheduling and troubleshooting that one.

The 60-second version, in either language: point it at your Secret Server with
an account that has View on something, run it with no arguments, and it lists
the folders it can see and stops. That is always a safe first run.

```powershell
.\Invoke-EnzoicDelineaScan.ps1                      # PowerShell
```
```console
$ enzoic-delinea                                    # Python
```

## Output

| Verdict | Meaning |
|---|---|
| `Compromised` | Enzoic matched the password and it was revealed in a breach. `Exposures` is the count |
| `Weak` | Enzoic matched the password but it was never exposed — known-weak |
| `Clean` | Checked against Enzoic, no match |
| `CheckFailed` | The lookup did not complete. **Not a pass**, and counted separately |
| *(blank)* | Not checked. The note says why: requires check-out, no password field, read error, or no API key |

Only the first 10 hex characters of each password's SHA-256 leave the machine.
The full hash is compared locally against the candidates Enzoic returns.

## Scope

This repository is the **vault sweep**: a point-in-time audit of what is
already in the vault.

It is not the Secret Server *event pipeline* integration, which is the other
half of the story — pipelines see one password at the moment it changes and can
block a pre-checkout or trigger a rotation. The two are complementary and the
pipelines are tracked separately.

For Active Directory accounts, the sweep is not the right tool either: Enzoic
for Active Directory hooks password-set at the domain controller and prevents a
compromised password from being set in the first place. This sweep exists for
the credentials AD never sees — the service accounts that live only in Secret
Server.

## Security notes

- **The config file holds a password that can read every secret in scope.**
  Both READMEs cover locking it down and encrypting the two secrets it carries.
  Both config files are gitignored.
- **Reports contain no passwords**, with or without `--reveal` / `-Reveal`.
  There is a test in each suite asserting it, because it is the one thing that
  must not regress: the report is the artifact that gets emailed. Reports are
  gitignored too — they are still an inventory of your credentials.
- **Keep reveal off in anything scheduled.** A transcript would otherwise
  capture every password in the vault.
- Neither integration writes to Secret Server, and neither checks out a secret:
  every read passes `noAutoCheckout=true`, and checkout-required secrets are
  skipped and reported as skipped rather than locked away under the API account.

## Tests

Both suites are fully offline — a fake Secret Server and a fake Enzoic on
localhost. No vault, no API key, no network, nothing external contacted.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\powershell\tests\Test-EnzoicDelineaScan.ps1
```
```console
$ python python/tests/test_delinea.py
```
